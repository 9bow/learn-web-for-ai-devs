SQLite로 빠르게 시작했다면 언제 PostgreSQL로 넘어가야 할까? 너무 일찍 전환하면 불필요한 복잡도를 추가하고, 너무 늦으면 데이터 손실이나 장애가 발생할 수 있다.

## 전환 신호

다음 중 하나라도 해당하면 PostgreSQL 전환을 고려할 시점이다.

```text
신호 1: "database is locked" 에러가 자주 발생한다
  → 여러 FastAPI 워커 또는 백그라운드 작업이 동시에 쓰기를 시도 중

신호 2: 실제 쿼리 지연·백업·복구 요구가 현재 구성의 한계를 넘는다
  → 파일 크기만으로 판단하지 않는다. SQLite에도 빌드·페이지 크기별 크기 제한이 있다

신호 3: 여러 서버가 같은 DB에 접근해야 한다
  → SQLite는 단일 파일이므로 네트워크 공유 불안정

신호 4: PostgreSQL 검색 기능·운영 체계가 요구에 더 적합하다
  → SQLite도 FTS5를 제공하므로 전문 검색 자체가 없는 것은 아니다

신호 5: 벡터 유사도 검색이 필요하다 (RAG, 임베딩 검색)
  → pgvector의 기능·운영 특성이 필요하다면 고려. SQLite도 별도 벡터 확장을 사용할 수 있다

신호 6: 복잡한 JSON 쿼리, 배열 타입이 필요하다
  → PostgreSQL의 JSONB, 배열 타입이 필요
```

## SQLAlchemy로 전환이 쉬운 이유

SQLAlchemy는 이식성을 높이지만 드라이버·스키마·타입·쿼리·트랜잭션·데이터 이관 검증이 필요하다.

```python
# database.py

# SQLite (개발)
DATABASE_URL = "sqlite:///./app.db"
engine = create_engine(
    DATABASE_URL,
    connect_args={"check_same_thread": False},
)

# PostgreSQL (프로덕션) — URL만 교체
DATABASE_URL = "postgresql://user:password@localhost:5432/mydb"
engine = create_engine(DATABASE_URL)  # connect_args 불필요
```

환경변수로 전환 지점을 제어한다.

```python
import os
from sqlalchemy import create_engine

DATABASE_URL = os.getenv("DATABASE_URL", "sqlite:///./app.db")

# DB별 풀 정책 설정. SQLAlchemy 2.x 파일 SQLite도 기본 QueuePool을 사용
if DATABASE_URL.startswith("postgresql"):
    engine = create_engine(
        DATABASE_URL,
        pool_size=10,
        max_overflow=20,
        pool_pre_ping=True,  # 연결 유효성 사전 확인
    )
else:
    engine = create_engine(
        DATABASE_URL,
        connect_args={"check_same_thread": False},
    )
```

## 호환성 주의사항

SQLAlchemy ORM은 대부분 추상화하지만, 일부 차이가 있다.

| 항목 | SQLite | PostgreSQL |
|------|--------|-----------|
| AUTOINCREMENT | `INTEGER PRIMARY KEY` | `SERIAL` 또는 `IDENTITY` |
| 불리언 | 0/1로 저장 | 네이티브 `BOOLEAN` |
| 날짜 타입 | 문자열로 저장 | 네이티브 `TIMESTAMP` |
| LIKE 대소문자 | 기본 무시 | 기본 구분 (ILIKE 사용) |
| JSON | JSON 함수·JSONB 지원. ORM 저장 방식 확인 | 네이티브 JSON·JSONB 지원 |
| 동시성 | 여러 연결·reader, writer는 한 번에 하나 | 여러 writer 가능, 연결 예산·잠금은 별도 관리 |

```python
# LIKE 쿼리 — PostgreSQL에서 대소문자 구분
# SQLite: WHERE name LIKE '%bert%' (대소문자 무시)
# PostgreSQL: WHERE name ILIKE '%bert%' (대소문자 무시)

# SQLAlchemy에서 이식 가능하게 작성
from sqlalchemy import func

# 방법 1: func.lower() 사용 (양쪽 DB 호환)
results = db.query(Experiment).filter(
    func.lower(Experiment.name).like(f"%{keyword.lower()}%")
).all()
```

## 마이그레이션 전략

데이터를 SQLite에서 PostgreSQL로 옮기는 절차:

```bash
# 1. PostgreSQL 설치 및 DB 생성
createdb myapp_db

# 2. pip 드라이버 설치
pip install psycopg2-binary

# 3. 환경변수 변경
export DATABASE_URL="postgresql://user:password@localhost:5432/myapp_db"

# 4. Alembic으로 스키마 생성
alembic upgrade head

# 5. 데이터 이전 (Python 스크립트)
```

```python
# migrate_data.py
import sqlite3
import psycopg2
from psycopg2.extras import execute_values

sqlite_conn = sqlite3.connect("app.db")
sqlite_conn.row_factory = sqlite3.Row

pg_conn = psycopg2.connect("postgresql://user:password@localhost:5432/myapp_db")

# 쓰기를 중지하고 백업한 원본을 사용한다. 비어 있는 대상 DB에 한 번만 실행한다.
with pg_conn.cursor() as cur:
    users = sqlite_conn.execute("SELECT id, email, hashed_password, created_at FROM users").fetchall()
    if users:
        execute_values(cur, "INSERT INTO users (id, email, hashed_password, created_at) VALUES %s",
                       [tuple(row) for row in users])
    rows = sqlite_conn.execute("SELECT * FROM experiments").fetchall()
    if rows:
        execute_values(
            cur,
            "INSERT INTO experiments (id, name, accuracy, owner_id, created_at) VALUES %s",
            [(r["id"], r["name"], r["accuracy"], r["owner_id"], r["created_at"]) for r in rows],
        )

    # 명시적 ID 복사 후 PostgreSQL의 다음 자동 ID를 원본 최댓값 이후로 이동
    cur.execute("SELECT setval(pg_get_serial_sequence('users', 'id'), "
                "COALESCE(MAX(id), 1), MAX(id) IS NOT NULL) FROM users")
    cur.execute("SELECT setval(pg_get_serial_sequence('experiments', 'id'), "
                "COALESCE(MAX(id), 1), MAX(id) IS NOT NULL) FROM experiments")
pg_conn.commit()
pg_conn.close()
sqlite_conn.close()
```

이 예제는 작은 DB의 일회성 이관이다. 사용자 테이블을 먼저 복사해 외래키를 만족시키고, ID sequence를 조정한다. 행 수·관계·날짜·불리언 값·최초 신규 INSERT와 애플리케이션 테스트를 확인한 뒤 전환한다. 대규모 DB에서는 전체 fetchall 대신 배치 이관과 실패 시 rollback·복구 절차를 작성한다.

## pgvector: PostgreSQL에서 벡터 검색

AI 엔지니어에게 PostgreSQL의 가장 큰 장점 중 하나가 pgvector다. LLM 임베딩을 DB에 저장하고 유사도 검색을 할 수 있다.

```bash
# pgvector 설치 (PostgreSQL 확장)
# Homebrew: brew install pgvector
# 또는 Docker 이미지: pgvector/pgvector:pg16

pip install pgvector sqlalchemy
```

```python
# models.py — pgvector 사용
# 먼저 해당 DB에서 CREATE EXTENSION vector를 실행할 권한과 확장 설치를 확인한다.
from pgvector.sqlalchemy import Vector
from sqlalchemy import Column, Integer, String, Text
from database import Base


class Document(Base):
    __tablename__ = "documents"

    id = Column(Integer, primary_key=True)
    content = Column(Text, nullable=False)
    embedding = Column(Vector(1536))  # OpenAI text-embedding-3-small 차원
```

```python
# 임베딩 저장
def store_document(db: Session, content: str, embedding: list[float]) -> Document:
    doc = Document(content=content, embedding=embedding)
    db.add(doc)
    db.flush()
    return doc


# 유사도 검색 (코사인 유사도)
def search_similar(db: Session, query_embedding: list[float], top_k: int = 5):
    return (
        db.query(Document)
        .order_by(Document.embedding.cosine_distance(query_embedding))
        .limit(top_k)
        .all()
    )
```

```sql
-- pgvector 인덱스 (대용량 데이터에서 ANN 검색)
CREATE INDEX ON documents USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);
-- 또는 HNSW (더 빠른 검색, 더 많은 메모리)
CREATE INDEX ON documents USING hnsw (embedding vector_cosine_ops);
```

## 핵심 정리

- **동시 쓰기 에러, 다중 서버, 벡터 검색이 필요하면 전환 시점이다** — 너무 일찍 전환할 필요는 없다
- **SQLAlchemy ORM을 사용했다면 드라이버·스키마·데이터·쿼리를 함께 검사해 전환한다** — SQL 직접 작성보다 이식성이 높다
- **LIKE vs ILIKE, 불리언 처리 등 미묘한 차이를 확인한다** — 특히 대소문자 검색에 주의한다
- **데이터 이전은 Alembic으로 스키마를 먼저 만들고, 스크립트로 데이터를 복사한다** — 순서가 중요하다
- **pgvector는 PostgreSQL에서 벡터 유사도 검색을 가능하게 한다** — RAG 파이프라인에서 별도 벡터 DB 없이 활용할 수 있다
