## 두 가지 서버의 역할

웹 서버(Web Server)와 WAS(Web Application Server)는 이름이 비슷해 혼동하기 쉽지만, 처리하는 일이 다릅니다.

```text
클라이언트
    │
    ▼
┌──────────────────────┐
│  Web Server (nginx)  │  ← 정적 콘텐츠, 라우팅, SSL
└──────────┬───────────┘
           │ 동적 요청만 전달
           ▼
┌──────────────────────┐
│  WAS (Uvicorn)       │  ← 비즈니스 로직, 모델 추론
│  FastAPI 앱          │
└──────────────────────┘
```

| 구분 | Web Server | WAS |
|------|-----------|-----|
| 대표 제품 | nginx, Apache | Uvicorn, Gunicorn, Tomcat |
| 처리 대상 | 정적 파일, 라우팅 | 동적 요청, 비즈니스 로직 |
| 언어 | C (고성능) | Python, Java, Node.js |
| 동시성 | 이벤트 루프, 수만 연결 | 프로세스/스레드 모델 |
| 상태 | Stateless | 상태 보유 가능 |

## Web Server: nginx가 잘하는 것

nginx는 C로 작성되어 메모리 효율이 높고 이벤트 기반으로 동작합니다. 수만 개의 동시 연결을 처리할 수 있습니다.

### 정적 파일 서빙

React 빌드 결과물(`/dist` 디렉토리)을 nginx가 직접 서빙하면 FastAPI까지 요청이 오지 않습니다.

```nginx
server {
    location / {
        root /var/www/html/dist;
        try_files $uri $uri/ /index.html;
    }
}
```

Python 프로세스를 거치지 않으므로 응답 속도가 훨씬 빠릅니다. 정적 파일은 Python이 처리할 이유가 없습니다.

### 버퍼링과 슬로우 클라이언트 보호

네트워크가 느린 클라이언트가 데이터를 천천히 받아가는 동안, nginx는 WAS로부터 응답을 미리 받아 버퍼에 저장합니다.

```text
[버퍼링 없을 때]
WAS ──응답 전송 중── 느린 클라이언트
↑ WAS 프로세스가 묶여있음 (느린 클라이언트 처리 동안)

[nginx 버퍼링]
WAS ──빠른 전송──▶ nginx 버퍼 ──천천히──▶ 느린 클라이언트
↑ WAS는 이미 해제됨
```

Uvicorn 프로세스가 느린 클라이언트 때문에 점유되는 것을 막아줍니다. 모델 추론 서버처럼 프로세스가 귀한 환경에서 중요합니다.

## WAS: Uvicorn과 Gunicorn

Python FastAPI 애플리케이션은 ASGI(Asynchronous Server Gateway Interface) 서버 위에서 동작합니다.

### WSGI vs ASGI

| 구분 | WSGI | ASGI |
|------|------|------|
| 동기/비동기 | 동기만 | 동기 + 비동기 |
| 대표 서버 | Gunicorn | Uvicorn |
| HTTP 스트리밍 | 동기 iterable로 가능 | 동기·비동기 처리 가능 |
| WebSocket | 미지원 | 지원 |

FastAPI는 ASGI 앱이므로 Uvicorn·Hypercorn 같은 ASGI 서버가 필요합니다.

### Uvicorn 단독 실행

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
```

위 명령은 한 워커를 실행합니다. Uvicorn은 프로덕션에서도 사용할 수 있으며 `--workers N`으로 다중 프로세스를 관리합니다. 동기 CPU 작업을 `async def`에 넣는다고 병렬 처리가 되지는 않습니다.

### Gunicorn + Uvicorn Worker 조합

기존 Gunicorn 운영 환경에서는 별도 `uvicorn-worker` 패키지를 설치합니다. Uvicorn 내장 `uvicorn.workers` 모듈은 폐기 예정입니다.

```bash
pip install gunicorn uvicorn-worker
gunicorn app.main:app \
  --workers 4 \
  --worker-class uvicorn_worker.UvicornWorker \
  --bind 0.0.0.0:8000 \
  --timeout 120      # 모델 추론 시간 여유
```

```text
Gunicorn (마스터 프로세스)
├── Uvicorn Worker 1 (FastAPI 앱)
├── Uvicorn Worker 2 (FastAPI 앱)
├── Uvicorn Worker 3 (FastAPI 앱)
└── Uvicorn Worker 4 (FastAPI 앱)
```

`2 × CPU_코어 수 + 1`을 ASGI·GPU 앱의 보편 공식으로 사용하지 않습니다. 워커 수별 처리량·p95 지연·모델 메모리를 측정합니다. 워커마다 모델을 로드하면 같은 GPU의 VRAM을 경쟁하므로 OOM이 발생할 수 있습니다.

### 모델 서빙 시 워커 설계

```bash
# 단일 웹 워커. 추론의 동시성·배치는 별도 정책으로 제한한다.
gunicorn app.main:app --workers 1 --worker-class uvicorn_worker.UvicornWorker
```

다음은 별도 HTTP 추론 서버로 요청을 전달하는 발췌 예제입니다.

```python
# Triton이라면 HTTP API는 통상 8000, gRPC API는 통상 8001을 사용한다.
@app.post("/predict")
async def predict(request: PredictRequest):
    # 모델 서버에 HTTP 요청으로 위임
    async with httpx.AsyncClient() as client:
        response = await client.post("http://model-server:8000/predict", ...)
    return response.json()
```

GPU 메모리는 프로세스 간 공유가 안 되므로, 워커를 늘리면 같은 모델이 메모리에 N번 로드됩니다.

## 책임 분리가 주는 실용적 이점

```text
[배포 시 역할 분담]

nginx:
  - /static/* → React 빌드 파일 직접 서빙
  - /api/*    → Uvicorn으로 프록시
  - SSL 종료
  - gzip 압축
  - 요청 크기 제한 (client_max_body_size)

Uvicorn + FastAPI:
  - /api/predict → 모델 추론
  - /api/users   → DB 조회
  - 인증 미들웨어
  - 입력 유효성 검사
```

이 분리 덕분에 nginx 설정 변경(예: SSL 인증서 갱신)은 FastAPI를 재시작하지 않아도 됩니다. FastAPI 코드 변경은 nginx를 건드리지 않습니다.

## 핵심 정리

- Web Server(nginx)는 정적 파일 서빙, SSL 종료, 라우팅을 담당한다. C로 작성되어 수만 동시 연결을 처리한다.
- WAS(Uvicorn)는 FastAPI 애플리케이션을 실행해 동적 요청과 비즈니스 로직을 처리한다.
- nginx의 버퍼링은 느린 클라이언트가 Uvicorn 프로세스를 점유하는 것을 방지한다.
- FastAPI는 ASGI 서버가 필요하다. Uvicorn의 내장 워커 관리 또는 Gunicorn과 별도 `uvicorn-worker` 패키지를 사용할 수 있다.
- GPU 모델은 워커마다 별도 메모리를 사용하므로, 워커를 늘리면 메모리 사용량이 비례해서 늘어난다. 단일 워커 + 별도 모델 서버 구조를 고려하라.
