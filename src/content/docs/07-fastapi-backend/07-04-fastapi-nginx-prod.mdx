개발 중에는 `fastapi dev`가 자동 재로딩과 상세 로그를 제공한다. 프로덕션에서는 재로딩을 끄고, 프로세스 재시작·TLS·로그·타임아웃·복제 전략을 별도로 설계해야 한다. 그렇다고 Gunicorn이 항상 필수인 것은 아니다. 현재 FastAPI 공식 문서는 `fastapi run --workers`와 `uvicorn --workers`를 직접적인 다중 프로세스 실행 방법으로 안내한다.

## 먼저 배포 단위를 결정한다

```text
┌──────────────────── 단일 VM / 베어메탈 ────────────────────┐
│ nginx ─▶ Uvicorn 부모 프로세스 ─┬─ worker 1              │
│                                 ├─ worker 2              │
│                                 └─ worker N              │
└────────────────────────────────────────────────────────────┘

┌──────────────────── 컨테이너 오케스트레이터 ────────────────┐
│ Load Balancer ─┬─ Pod A: Uvicorn 1 process               │
│                ├─ Pod B: Uvicorn 1 process               │
│                └─ Pod C: Uvicorn 1 process               │
└────────────────────────────────────────────────────────────┘
```

단일 VM에서는 한 부모 프로세스가 여러 워커를 관리하는 구성이 단순하다. Kubernetes 같은 오케스트레이터에서는 컨테이너 자체가 복제·재시작 단위이므로 보통 컨테이너당 Uvicorn 프로세스 하나를 두고 Pod 수를 늘린다. 컨테이너 안과 오케스트레이터 양쪽에서 동시에 복제하면 용량 계산, 종료 신호, 헬스 체크가 불필요하게 복잡해진다.

## 단일 서버: FastAPI CLI 또는 Uvicorn

`fastapi[standard]`를 설치했다면 다음과 같이 실행할 수 있다.

```bash
fastapi run --workers 4 main.py
```

Uvicorn을 직접 실행하는 방법도 같다.

```bash
uvicorn main:app \
  --host 127.0.0.1 \
  --port 8000 \
  --workers 4 \
  --proxy-headers \
  --forwarded-allow-ips 127.0.0.1
```

여기서 중요한 점은 다음과 같다.

| 옵션 | 역할 | 주의점 |
|---|---|---|
| `--workers 4` | 별도 프로세스 네 개로 요청 처리 | 앱과 모델 메모리도 워커마다 복제될 수 있다 |
| `--host 127.0.0.1` | nginx가 같은 호스트에서만 접근 | 외부에 직접 노출하지 않는다 |
| `--proxy-headers` | `X-Forwarded-*` 헤더 반영 | 신뢰할 프록시를 반드시 제한한다 |
| `--forwarded-allow-ips` | 프록시 헤더를 믿을 IP 지정 | `*`는 신뢰 경계가 명확할 때만 사용한다 |

`Uvicorn은 개발 전용`이라는 설명은 정확하지 않다. Uvicorn은 프로덕션 ASGI 서버로 사용할 수 있다. 다만 외부에 직접 노출하기보다 nginx나 관리형 로드밸런서 뒤에 두고, systemd·컨테이너 런타임·오케스트레이터 중 하나가 재시작과 수명 주기를 맡게 한다.

## 워커 수는 공식으로 정하지 않는다

`CPU 코어 × 2 + 1`은 모든 ASGI 앱에 적용되는 규칙이 아니다. 적절한 워커 수는 요청의 CPU 사용량, 블로킹 I/O, 메모리, 모델 로딩 방식, 목표 지연 시간에 따라 달라진다.

```text
1. 워커 1개로 부하 테스트
2. 워커를 2, 4개로 늘리며 처리량과 p95 지연 측정
3. 메모리 사용량과 CPU 포화 확인
4. 처리량 증가가 멈추거나 지연이 악화되기 직전 값을 선택
```

특히 ML 모델을 FastAPI 프로세스 안에 로드하면 워커마다 가중치가 복제될 수 있다. GPU 모델은 여러 웹 워커가 하나의 GPU 메모리를 경쟁하게 만들기보다, FastAPI와 전용 추론 서버를 분리하는 편이 일반적으로 안전하다.

## nginx 리버스 프록시

다음 예시는 TLS를 nginx에서 종료하고 FastAPI에 전달한다. 인증서 발급과 키 권한 관리는 별도 운영 절차로 다뤄야 한다.

```nginx
upstream fastapi_app {
    server 127.0.0.1:8000;
    keepalive 32;
}

server {
    listen 80;
    server_name api.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    http2 on;
    server_name api.example.com;

    ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;

    client_max_body_size 50m;

    location / {
        proxy_pass http://fastapi_app;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_connect_timeout 10s;
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }

    location /stream/ {
        proxy_pass http://fastapi_app;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_buffering off;
        proxy_cache off;
        add_header X-Accel-Buffering no;
        proxy_read_timeout 300s;
    }
}
```

`proxy_buffering off`는 모든 응답에 무조건 적용할 설정이 아니다. 일반 JSON 응답은 버퍼링이 처리량에 유리할 수 있으므로 SSE나 토큰 스트리밍 경로에만 끄는 편이 낫다. 스트림 중간에는 이미 HTTP 상태와 헤더가 전송되었으므로, 오류를 SSE 이벤트나 애플리케이션 프로토콜로 전달해야 한다.

설정 반영 전에는 반드시 문법을 검사한다.

```bash
sudo nginx -t
sudo systemctl reload nginx
```

## systemd로 수명 주기 관리

단일 VM에서는 systemd가 부팅 시 시작과 실패 후 재시작을 담당할 수 있다.

```ini
[Unit]
Description=FastAPI application
After=network.target

[Service]
Type=simple
User=www-data
Group=www-data
WorkingDirectory=/var/www/myapp
Environment="PATH=/var/www/myapp/.venv/bin"
ExecStart=/var/www/myapp/.venv/bin/fastapi run --workers 4 main.py
Restart=on-failure
RestartSec=5s
TimeoutStopSec=30s
KillSignal=SIGTERM

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now myapp
sudo systemctl status myapp
```

애플리케이션이 종료 신호를 받으면 새 요청 수락을 멈추고 진행 중인 요청을 마칠 시간이 필요하다. 서비스 관리자, nginx, 오케스트레이터의 종료 유예 시간이 서로 모순되지 않는지 함께 확인한다.

## Gunicorn을 쓰는 기존 환경

이미 Gunicorn의 훅, 로깅, 운영 도구에 의존하는 시스템이라면 계속 사용할 수 있다. 다만 Uvicorn 문서에서 `uvicorn.workers` 모듈은 폐기 예정으로 안내되므로 새 구성은 별도 `uvicorn-worker` 패키지의 worker class를 검토한다. 새 프로젝트에서 단지 다중 프로세스만 필요하다면 FastAPI CLI나 Uvicorn의 내장 `--workers`가 더 단순하다.

## 컨테이너와 Kubernetes

컨테이너 이미지에는 실행 파일과 앱만 넣고, TLS와 외부 로드밸런싱은 플랫폼 계층에 맡기는 구성이 일반적이다.

```dockerfile
FROM python:3.13-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .

CMD ["fastapi", "run", "main.py", "--port", "8000"]
```

Pod 복제 수, readiness/liveness probe, 리소스 요청·제한, 롤링 업데이트 전략은 배포 매니페스트에서 관리한다. 모델을 각 Pod에 로드한다면 시작 시간과 메모리 요구량을 readiness probe와 용량 계획에 반영한다.

## 검증 체크리스트

- [ ] 개발용 `--reload`가 프로덕션 명령에 없는가
- [ ] 프록시 헤더를 신뢰하는 IP 범위가 실제 프록시로 제한되어 있는가
- [ ] 일반 응답과 스트리밍 경로의 버퍼링 정책을 분리했는가
- [ ] 부하 테스트로 워커 수와 메모리 사용량을 측정했는가
- [ ] 단일 VM에서는 systemd 등 프로세스 관리자가 재시작을 담당하는가
- [ ] Kubernetes에서는 컨테이너 내부 워커 수와 Pod 복제를 중복 설계하지 않았는가
- [ ] 종료 유예 시간 안에 진행 중 요청이 안전하게 끝나는가

## 핵심 정리

- 단일 서버에서는 `fastapi run --workers N` 또는 `uvicorn --workers N`으로 여러 프로세스를 실행할 수 있다.
- Kubernetes에서는 일반적으로 컨테이너당 단일 Uvicorn 프로세스를 두고 Pod를 복제한다.
- nginx는 TLS 종료와 리버스 프록시를 담당하며, 스트리밍 경로에만 버퍼링을 끈다.
- 워커 수는 고정 공식이 아니라 부하 테스트, 메모리, 모델 배치 방식으로 결정한다.
- Gunicorn은 선택지이지 필수 조건이 아니며, 기존 `uvicorn.workers` 경로의 폐기 예정 상태를 고려해야 한다.
